# 长程自完善：零先验自举设计草案

> 状态：设计草案（未落地，v2）
> 定位：LongLoop 面对**零素材项目**（无 AGENTS.md / 无 CI / 无测试 / 无 lint 配置 / 文件名混乱）时的通用设计
> 原则：不依赖本项目已有机制与素材假设，面向任何陌生仓库的通用自举方案
> v2 变更：引入 copilot-sdk 调研启示；问询全部前移为**一次性 Onboarding 协议**；循环期**零问询**（支持几十~几百小时无人值守）；预授权分级 L1/L2/L3

---

## 一、问题背景

LongLoop 以门童为核心调度。开源用户拿到本项目后跑 `long-loop.ps1`，但**目标项目可能没有任何可参考素材**：

- 没有 AGENTS.md / CONTRIBUTING.md / README
- 没有 CI、测试、lint 配置、package.json
- 文件名可能是任何样子（`asdf123.txt`、无扩展名、混乱命名）

因此「发现项目的既有标准」这条路是错的——**当什么都没有时，必须由系统自己创造标准**。

## 二、外部调研结论（行业共识）

### 2.1 自完善类机制

调研对象：GitHub Copilot coding agent、SWE-agent / mini-swe-agent、Super Agent、agentic-workflow-template、autoimprove、Sequoia、look-for-work、desloppify、code-autopsy、architect、codebase-health-score、CodeScene、Implera、repowise、arXiv 2607.13070（Falsifiable Release Gates）。

**1. 任务来源 = 用户定义，AI 不自由决定「改什么」**
- Copilot / SWE-agent / Super Agent：用户写 issue → agent 执行 → PR，没人让 AI 自己找活
- 审计型工具（look-for-work、Sequoia、desloppify）做**只读扫描 → P0-P3 优先级队列**，修复仍需人点头
- 结构性/高风险改动普遍加人工审批门

**2. 「好」必须机器可判，不能自评（self-grading）**
- autoimprove：「Describe what to improve, how to measure it, and walk away」——用户定义改进什么+如何衡量，循环跑 benchmark，**提分保留、降分 git reset**
- arXiv 2607.13070：自完善系统的安全主张几乎都是自评分不可信；解 = 每个能力上线前过**预声明机器可检查的验收套件**；**收紧改动可自动应用，放松改动必须人工合并**
- desloppify：评分专门**抗游戏化**——只有真正改进代码才能提分

**3. 健康度分析的两条路线**
- 清单派：固定维度加权分（NxCode 8 维、look-for-work 15 维度、code-autopsy 16 诊断）
- 确定性派：语言无关统计 marker（repowise 25 marker、复杂度/死代码/重复/文档覆盖率），不依赖 LLM 主观判断

**4. 趋势 > 绝对值**（CodeScene）：绝对分不可信，连续改进趋势才是信号。

### 2.2 GitHub Copilot SDK 的启示

- **生产级形态 = 「定义行为 + 运行时自动规划执行」**：开发者写 agent 行为定义，SDK 运行时处理规划、工具调用、文件编辑——本项目等价物：opencode 是运行时，门童提示词是行为定义
- **指令/上下文外置为规范文件**（AGENTS.md 级指令 + 多语言指令文档），不塞进提示词——门童防臃肿的正解是把协议外置
- 支持 BYOK（自备 key）+ 自定义 agents/skills/tools：开源项目让用户自带 key 是成熟做法

## 三、核心反转：三层自举，不依赖任何先验

### 第 1 层 · 内容探测，不认文件名

文件名乱、无配置文件，都没关系——分析**内容**，不分析**命名**：

- 文件字节特征 → 语言猜测（shebang、语法模式、扩展名统计）
- 语言无关的统计启发式（确定性检查器，任何目录可跑）：
  - 超长文件 / 超长函数（正则估算嵌套深度与长度）
  - 重复代码块
  - TODO / FIXME / HACK 密度
  - 空 catch / 吞错模式
  - console.log 泄漏
  - 硬编码 secret 模式
  - `|| true` 吞失败
- 产出：**健康快照 = 基线**（不管多烂，先记录）

### 第 2 层 · 创造验收探针，而不是等待验收层

项目没有测试/CI/入口 → **AI 为它构建最小可执行验收层**（参照 autoimprove：检测到无 eval harness → 交互式构建）：

- 语法探针：对每个源文件生成 parse/compile check
- 冒烟探针：识别入口（或 Onboarding 时用户一句话告知运行方式）后，生成最小 run 探针 + 退出码检查
- 探针由 AI 编写、机器可判、存入项目探针目录、**可被用户审查**
- 从此「好」有了可执行定义，且不依赖项目预先声明任何东西

### 第 3 层 · 相对趋势，不设绝对标准

不知道什么叫「好」没关系，知道「比上一轮好」就行：

- 首轮快照 = 基线
- 每轮改动后重新快照 → 与基线 diff → **完善 = 单调不回退 + 探针全绿**
- 绝对分无意义，趋势有意义；用户不需要理解任何技术指标

## 四、「好」与「完善」的定义（裁决权归属）

| 概念 | 定义 | 判定方 |
|------|------|--------|
| 完善 | 探针全绿 + 健康快照单调不回退 | 机器（确定性检查器，无需人在场） |
| 好 | 预授权范围内的改进集合（Onboarding 时一次性授予） | 用户（启动时定边界）+ 机器（边界内自动判定） |
| 改什么 | 体检产出的假设清单（带证据：文件+行号+统计） | AI 生成候选，按授权分级 |

**AI 永远不自我裁决「这就算好了」**——用户通过 Onboarding 授权边界一次性裁决，循环内不再需要用户在场。

## 五、Onboarding 一次性问询协议（问询全部前移）

循环期**零问询**，所有需要用户的信息在首次启动的一次性引导中全部问清：

| 问什么 | 为什么 | 答不了时默认 |
|---|---|---|
| 项目是干什么的？怎么运行？ | 冒烟探针的唯一信息来源 | 声明「未知」→ 循环只做静态层，不硬跑 |
| 目标（可选） | 有目标则定向，无目标则自完善 | 无 → 自动体检 + 趋势优化 |
| 改进方向偏好 | 决定假设生成的方向权重 | 全维度均权 |
| **授权边界**（能改什么/红线） | 循环内 AI 的自决策空间 | 最保守：只读 + 小步改进 |
| 资源预算（轮数/小时/成本） | 停机条件 | 默认 200h 经济模式 |

Onboarding 产物：授权规则集（预授权分级）+ 边界声明，落盘为状态文件，此后循环完全自主。

## 六、循环期零问询：预授权分级

遇到需要决策的事，不打断循环，按 Onboarding 预授权分级自决策：

- **L1 自动做**（预授权内）：探针绿、趋势不回退、低风险改进 → 直接执行
- **L2 保守默认做**：改动有副作用但可回滚（git reset / 探针兜底）→ 做，但留回滚点
- **L3 挂起不阻塞**（超出授权/破坏性/语义未知）：**写进挂起清单，循环继续做别的**，收尾时一次性交给用户裁决——不打断无人值守

## 七、完整循环

```
[Onboarding 一次性] 问清 5 项 → 生成授权规则 + 边界
        ↓
[无人值守循环，零问询，几十~几百小时]
内容探测（零先验统计）
  → 健康快照 = 基线
  → 生成改进假设清单（带证据）
  → 按预授权分级：L1/L2 自动执行 | L3 进挂起清单
  → 构建/运行验收探针（按需）
  → 重跑快照 → 与基线趋势对比（不回退才保留，可回滚）
  → 下一轮（直到预算用尽 / 无假设 / 全绿收敛）
        ↓
[收尾] 汇总交付：足迹（改了哪些）+ 挂起清单（待用户裁决）+ 后续建议
```

门童职责：路由 + 调度；协议外置为规范文档（不塞进提示词）；所有判定要么机器可判（探针/快照/趋势），要么 Onboarding 预授权（边界内自动执行）——**循环内没有任何 AI 主观维度，也不需要用户在场**。

## 八、兜底原则

> 能探测的探测，探测不了的 Onboarding 问清，Onboarding 也问不到的挂起不阻塞。
> 绝不硬猜——猜错方向比等待更浪费（会烧资源改错东西）；挂起清单在收尾时统一裁决，不中断长程循环。

## 九、开放问题（待定）

1. Onboarding 交互形态：交互式向导 CLI vs 配置文件模板（如 `longloop.config.json`）？——推荐两者都支持，向导生成配置
2. 探针目录的默认位置与命名、是否进 .gitignore
3. 假设清单的上限与去重策略（避免清单爆炸）
4. 挂起清单的容量与轮转（长期运行下 L3 堆积的收敛策略）
5. 用户中途修改目标/边界：支持热更新（读状态文件变化），但不打断循环
6. 与现有 LongLoop 状态协议（state.json / 足迹.md / blockers）如何嫁接——本草案为纯通用设计，嫁接时另行决定
7. 授权边界的默认值是否分风险档（如只读档 / 小步档 / 全权档）供用户一键选择
