OpenCode MoAは、OpenCodeのためのエージェントの混合構成パッケージです。複数のモデルが**同じ問題について同時に考える**ことを可能にし、単一のモデルでは到達できない出力品質に融合します。ツールを切り替えたり、コードを書いたり、APIのクォータを持ったりする必要はありません — 単にファイルをプロジェクトにドロップし、OpenCodeを再起動してください。

**22エージェント · 5コマンド · 3スキル · 30秒デプロイ**

---


## なぜこれが必要ですか？

デフォルトでは、OpenCodeは最初から最後まで単一のモデルを使用します。1文字を変更し、システムアーキテクチャを設計するのに同じプロンプト、同じ温度、同じコンテキストを使用します。労働の分担はありません。

**3つの問題:**

1. **コストが制御不能** — 単純なタスクも高価なモデルを使用し、月々の請求が高止まりする
2. **品質のボトルネック** — 単一のモデルは思考の方法が1つしかなく、盲点に簡単にハマる
3. **フォールトトレランスがない** — モデルが死ぬとフリーズし、フォールバックがない

**MoAの解決策:**

```

You: メッセージキューソリューションの設計を手伝ってください

    ┌─ flag-arch (Qwen3.7 Max)  ─── アーキテクトの視点からの計画
    ├─ flag-plan (GLM 5.2    )  ─── PMの視点からの計画
    ├─ flag-eng  (MiniMax M3 )  ─── 実装者の視点からの計画
    └─ flag-fuse (Kimi K3    )  ─── 各モデルの最良の部分を取り入れ、最適な解決策を提供
```

3つの異なるモデルからの3つの独立した計画が自然に「コンセンサス + ダイバージェンス」の構造を形成します。フュージョンモデルはコンセンサスを特定し、それを保持し、彼らが異なる部分での最良のものを取り入れます — これは単一のモデルではできません。

### デスクトップ vs CLI

- **CLI**: すべてのメソッドがサポートされています
- **デスクトップ**: メソッド1（AI自動デプロイ）が最も便利です; メソッド2/3は最初にターミナル操作が必要です

> ⚠️ **システムレベルのキーのパスを間違えて配置するのは簡単です** — 下記の「デプロイ前に読む」で正しいスペルを確認してください。間違ったパスは、デプロイが成功したように見えてもすべてのエージェントが接続できなくなります。

> ⚠️ **デプロイ前に読む: キーパスを間違えないでください**
> プロバイダー + キーを**プロジェクトレベルの `opencode.json`**（デフォルト、自己完結型）または**システムレベル**の共有パスのいずれかに配置してください — **1つだけ**選択してください。
> システムレベルを使用する場合、正しいパスは次の通りです:
> 
> - Linux/macOS `~/.config/opencode/opencode.json`
> - Windows `%USERPROFILE%\.config\opencode\opencode.json` (**not** `%APPDATA%\opencode`)
>   間違ったシステムレベルのパスは「デプロイが成功したがすべてのエージェントが接続できない」ことにつながります。

## 30秒デプロイ

### メソッド1: AI自動デプロイ（推奨）

1. [`docs/opencode-moa.en.md`](https://github.com/ZenHG/opencode-moa/blob/master/docs/opencode-moa.en.md)をダウンロード
2. そのドキュメントをOpenCodeにアップロードし、送信:

> このマニュアルから22のエージェント、5つのコマンド、3つのスキルを現在のプロジェクトにデプロイします

3. AIがすべてのファイルを自動的に作成します。**完了したらOpenCodeを再起動してください。**

> 手動でファイルを作成する必要はありません。デプロイマニュアル自体がインストーラーです。

### メソッド2: ワンクリックインストールスクリプト（スクリプト版 · CLIフレンドリー）

```bash
# リポジトリをクローン
git clone https://github.com/ZenHG/opencode-moa.git

# プロジェクトディレクトリに入る
cd your-project

# リポジトリから .opencode ディレクトリと .moa 設定をコピー
cp -r ../opencode-moa/.opencode/ .
cp -r ../opencode-moa/.moa/ .

# インストールスクリプトを実行（設定を自動マージし、APIキーを保持）
# Windows:
pwsh ../opencode-moa/install.ps1
# Linux/macOS:
bash ../opencode-moa/install.sh
```

> インストールスクリプトは元の `opencode.json` を自動バックアップし、プロバイダーとAPIキーを保持しながらMoA設定のみをマージします。
> 
> 注意: この方法ではリポジトリのバンドルされた `.opencode/` をそのままコピーします — そのエージェントは**中国語の表示名**を持っています。英語名のエージェントが必要な場合（`@english-name`を使用できるようにするため）、メソッド1を使用してください。

### 任意のモデルをカスタマイズ

MoAは**汎用テンプレート**です — 各エージェントのモデルは変更可能なIDです。各エージェントファイルは次のように始まります:

```yaml
model: opencode-go/<model-id>
```

モデルを入れ替えるには、`.opencode/agents/<agent>.md`のその1行を、アクセス可能な任意の`provider/model-id`に編集します（例: `opencode-go/kimi-k2.7-code`, `opencode-go/glm-5.2`）。再インストールは不要です。自由に組み合わせてください — テンプレートは何にも縛られません。

### メソッド3: 手動インストール

```bash
# 1. リポジトリをクローン
git clone https://github.com/ZenHG/opencode-moa.git

# 2. .opencode ディレクトリと .moa 設定をコピー
cp -r opencode-moa/.opencode/ your-project/

# 3. opencode.jsonを手動でマージ（直接置き換えないでください！）
# opencode.jsonを開き、MoAのpermission.taskとagentセクションをマージします

```

> ⚠️ **cat >>** を使用して追加しないでください — JSON形式が壊れます。**直接置き換えないでください** — APIキーを失います。
> 
> 注意: この方法ではリポジトリのバンドルされた `.opencode/` をそのままコピーします — そのエージェントは**中国語の表示名**を持っています。英語名のエージェントが必要な場合（`@english-name`を使用できるようにするため）、メソッド1を使用してください。

1. OpenCodeを再起動した後、`Tab`を押してエージェントを循環させ（Windowsデスクトップクライアントでは `Ctrl+.` も機能します）、「concierge-router」を確認します

## アーキテクチャ

```
                      concierge-router (Flash)
                                 │
                ┌────────────────┼─────────────────┐
                ▼                ▼                 ▼
             ツール層         意見層             融合層
             Flash + MiMo   3つの並列意見が最良を選択
             (~80% コール)   (~18% コール)        (~2% コール)
```

**ツール層** (Flash + MiMo) — コードを読み、ファイルを検索し、スクリーンショットをテキストに変換します。安価で迅速、自由に呼び出せます。

**意見層** (MiniMax / DeepSeek Pro / Qwen / MiMo-Pro) — 異なる視点からの計画。3つの意見が自然に「合意 + 分岐」の構造を形成します。

**融合層** (Kimi K3 / Qwen-Max / GLM / DeepSeek Pro フォールバック) — 合意を維持し、分岐の中で最良を選択し、融合が失敗した場合はDeepSeek V4 Proにフォールバックします。フラッグシップの融合は現在 **Kimi K3** (2.8T パラメータ, 1M コンテキスト, トップティアのフロンティアモデル) で動作しており、MoAの品質の上限を引き上げています。

> ⚠️ 以下のコールボリューム比率 (~80% / ~18% / ~2%) は **設計目標** であり、測定された統計ではありません。実際の比率はタスクの複雑さによって異なります。

### 構造化出力

意見および融合エージェントは `---section-name---` マーカーを使用します。意見層: `---memory---` + `---plan---` + `---NOT---`。融合層: メタデータ、合意、計画、NOTリストおよび受け入れ基準を含む完全な構造。下流の解析と凍結された受け入れの検証を可能にします。

### アンチチート (v0.0.15)

実装エージェントが手を抜くのを防ぎます: ベースラインの非回帰、禁止行動（テストのスキップ/モック/削除）、隠れたスポットチェック、実装の差分チェック、ストップロス（アイテムごとに3回のリトライ、回帰時のロールバック）。受け入れ基準テンプレートは `.moa/acceptance-template.json` にあります。

## フォールトトレランス設計

### ツールレイヤーフォールバックチェーン

ツールレイヤーが失敗してもフリーズせず — 自動的にダウングレードします:

```
tool-handler (Flash) failed → immediate retry once
  → retry succeeds → return normally
  → retry fails → tool-handler-mimo (MiMo) failed → immediate retry once
    → retry succeeds → return normally
    → retry fails → ask user:
      A. wait a few minutes and retry
      B. skip tool layer, call opinion layer directly (higher cost)
      C. switch to free model
```

> ほとんどのプロバイダーエラー (502/503/タイムアウト) は一時的なものであり、迅速な再試行は通常成功します。

### フュージョンレイヤーフォールバック

プライマリフュージョンエージェントが失敗した場合 (STUCK / ERROR_PROVIDER / タイムアウト / 空の結果)、コンシェルジュルーターは自動的に `@融合·保底` (DeepSeek V4 Pro, フォールバック) にフォールバックします:

```
flag-fuse (旗舰·融合, Kimi K3) failed
  → task(@融合·保底) (DeepSeek V4 Pro) → output fallback result
mid-fuse (中级·融合, Kimi) failed
  → task(@融合·保底) (DeepSeek V4 Pro) → output fallback result
fe-lead (前端·总工, GLM-5.2) failed
  → task(@融合·保底) (DeepSeek V4 Pro) → output fallback result
```

フォールバックエージェントは、同じ残差強化フュージョンプロセスを使用します。

### 意見レイヤー部分的失敗耐性

個々の意見エージェント (アーキテクチャ/計画/エンジニアリング、フロントエンド復元/ロジック/モーション、中級エンジニアリング/クリエイティブ/コーディング) は、独立して空の結果を返したり、タイムアウトしたりすることがあります。システムはこれを優雅に処理します:

```
3 parallel opinion agents dispatched
  → any agent returns empty result → retry that agent once
    → retry succeeds → continue normally
    → retry fails → mark as "degraded" and proceed with N/3 inputs
      → 残差提取者 works with available inputs only
      → 旗舰·融合 applies degraded fusion rules
      → output carries "[Partial] N/3 inputs" label
      → confidence score is adjusted downward
```

劣化したフュージョンルール (N < 3):
- コンセンサスカバレッジの分母は N であり、3 ではありません
- 欠落している視点は `[Missing: perspective name]` とラベル付けされます
- コンセンサスカバレッジ < 50% は「低信頼度の劣化フュージョン」警告をトリガーします
- 単一ソースフュージョン (N=1) は 0.7 の信頼度ペナルティファクターを適用します

> これは、1 つの意見エージェントが失敗したときにパイプラインが停止するのを防ぎます (STUCK) — よくあるユーザーの不満です。

### 宣言的エージェント前提条件

エージェントのアクティベーションは、ハードコーディングされたルーティングルールではなく、宣言的な `precondition` メタデータによって管理されます。各エージェントは、いつアクティブにすべきかを宣言します:

| エージェント | 前提条件 |
|-------|---------------|
| 闪电侠 | いつでも |
| 工具人 | コードベースのコンテキストが必要 |
| 视觉翻译官 | プライマリ: `screenshot`; フォールバック: `error_log OR diagram OR long_document OR ambiguous_intent` |
| 中级·工程 | エンジニアリングの複雑さが必要 |
| 中级·创意 | クリエイティブな複雑さが必要 |
| 中级·码农 | 実装の複雑さが必要 |
| 旗舰·架构/规划/工程 | システム設計の複雑さが必要 |
| 前端·还原/逻辑/动效 | フロントエンドタスクが必要 |
| 融合·保底 | フュージョンレイヤーが失敗したとき、または意見レイヤーが部分的な結果を返したときにアクティブ化されます |

条件のアクティベーションはショートサーキットロジックに従います: 前提条件が満たされる → アクティブ化; 満たされない → ユーザーに確認を求める。これにより、ハードコーディングされたトリガールール (「スクリーンショットが利用可能 → @vision-translator」など) が、エージェントが宣言した自己文書化された前提条件に置き換えられます。

### パイプラインステージの視覚化

すべてのルーティング決定はステージ識別子を出力し、ユーザーが内部のステップ番号を学ぶことなくパイプラインの進行状況を追跡できるようにします:

```
[Stage: Tool Layer] → [Stage: Opinion Layer] → [Stage: Fusion Layer] → [Stage: Implementation Layer]
```

ステージとフェーズのマッピング:
- `Tool Layer` — 材料収集フェーズ
- `Opinion Layer` — 並列計画設計フェーズ (中級 / 旗舰 / フロントエンド)
- `Fusion Layer` — 計画の融合と検証フェーズ
- `Implementation Layer` — コード実装と受け入れフェーズ

### 統一された進捗報告

成功と失敗の両方のパスは同じ報告形式に従い、内部エージェント名を決して公開しません:

```
[Pipeline] mode=<lite|balanced|strict>  stage=<Tool Layer|Opinion Layer|Fusion Layer|Implementation Layer>  status=<idle|in_progress|complete|degraded|stuck>
  reason: <why this stage>
  path: <Tool Layer|Mid-tier chain|Flagship chain|Frontend chain>
  fallback: <recovery strategy>
```

ステータスインジケーター:
- `in_progress` — 現在のステージを実行中
- `complete` — ステージが正常に終了
- `degraded` — 部分的な入力で実行中、信頼度が低下
- `stuck` — すべての回復パスが尽き、ユーザーの介入が必要

### スウィフトパラレルショートカット

メインパイプラインが実行中のとき、スウィフトは独立した単純なサブタスクのために並行して派遣できます:

```
Main pipeline: Tool Layer → Opinion Layer → Fusion Layer → Implementation Layer
Parallel lane: swift (always ready, runs alongside main pipeline)
```

トリガー条件 (いずれか一つ):
- ユーザーの指示が明示的に並行作業を要求する ("同時に X を行う", "Y をすぐに確認する")
- メインパイプラインの実行中に単純なサブタスクが発生する (例: アーキテクチャ計画が設計されている間に TODO を検索する)
- ユーザーが直接 @swift を呼び出す

スコープ制限:
- ✅ メインパイプラインの出力に依存しない独立したタスク
- ✅ 単純な操作: ファイル検索、grep、設定クエリ、フォーマット
- ❌ メインパイプラインの入力を生成するタスク
- ❌ 意見フュージョンタスク (直列でなければならない)
- ❌ 実装および QA タスク (直列でなければならない)

スウィフトがメインパイプラインよりも早く終了した場合、結果は保持され、最後にまとめて返されます。メインパイプラインが先に終了した場合、スウィフトの結果は即座に返されます。スウィフトの失敗はメインパイプラインの実行に影響を与えません。

### MCP権限の分離

意見レイヤーのエージェントは、コードを直接読み取ることを禁止されています (`read: deny` + `bash: deny`)、これにより、ツールレイヤーをバイパスして自分で材料を取得することができなくなります:

- ツールレイヤー: コードを読み取り、ファイルを検索できます (`read`/`bash` アクセスあり)
- 意見レイヤー: `read: deny` + `bash: deny`、ツールレイヤーからの材料に基づいてのみ計画できます
- フュージョンレイヤー: 同じ制限があり、3つの意見に基づいてのみ融合できます

> 注: このプロジェクトは、MCPサーバーを構成していません。「MCP権限の分離」という用語は、エージェントレベルのツール制限 (`read: deny` / `bash: deny`) を指し、MCPサーバーレベルの分離ではありません。

### タスクネスティング防御

すべての非ルーティングエージェントは `task: deny` を宣言し、子エージェントが再度 task() を呼び出すのを防ぎ、再帰的なネスティングをブロックします:

- **レイヤー 1 (エージェントフロントマター)**: 各エージェントファイルは `task: deny` を宣言します
- **レイヤー 2 (opencode.json)**: `permission.task` はコンシェルジュがエージェントを呼び出すことのみを許可し、非ルーティングエージェントはワーカーを呼び出すことを全体的に禁止されています
- **レイヤー 3 (プロンプトガード)**: コンシェルジュプロンプトは、サブエージェントを介して新しいパイプラインを起動することを禁じる制約で終了します

> 2026-07 に追加。コンシェルジュ→tool-handler→tool-handler の三重ネスティングを発見した後。三層の冗長性により、1つのレイヤーが失敗してもブロックが保証されます。

### 無材料フォールバック

意見レイヤーが呼び出されるが材料がない場合 (ツールレイヤーが完全に失敗した場合)、ユーザーに尋ねます:

- 「計画を直接提供する」を選択 → 要件の説明に基づく純粋な論理的推論 (コードの読み取りなし)
- 「ツールレイヤーを待つ」を選択 → WAITING を出力し、ツールレイヤーが回復した後に再試行

### エラー分類

ツールレイヤーは失敗時に明確なエラーカテゴリを出力し、盲目的に再試行するのではなく:

- `ERROR_PROVIDER` — サーバー 502/503/タイムアウト
- `ERROR_AUTH` — 認証失敗
- `ERROR_UNKNOWN` — その他のエラー

## コスト

### 約90%の節約理由

MoAはコールボリューム加重ミックスで請求します：ツールレイヤーの約80%、ミッドティアの約18%、フラグシップの約2%。このセクションのコストテーブルの単位価格を使って、実効出力単価を推定します：

> **重要**：80/18/2の比率は**アーキテクチャによって設計された期待コールボリューム分布**であり、測定されたコスト比率ではありません。実際の使用はタスクの種類と複雑さに依存します。

| レイヤー      | シェア | 出力単位価格 /1M                                                                            | 加重   |
| ---------- | ----- | ------------------------------------------------------------------------------------------------ | -------- |
| ツールレイヤー | 80%   | $0.28                                                                                            | $0.224   |
| ミッドティア   | 18%   | ~$2.10 (MiniMax $1.20 / DeepSeek Pro $3.48 / Qwen Plus $1.60 / **Kimi K2.7 $4.00 mid-fuse** 平均) | $0.378   |
| フラグシップ   | 2%    | ~$6.00 (Qwen/GLM/MiniMax ~$4-7 + **Kimi K3 $15.00 flag-fuse**)                                   | $0.12    |

ブレンドされた実効出力単価 ≈ **$0.72 / 1M**。 "全フラグシップ GLM $7.50" と比較して → 約10% → **約90%の節約**; "全ミッドティア DeepSeek Pro $3.48" と比較して → 約21% → **約79%の節約**。 "90%の節約"という主張は、フラグシップベースラインに対する実際の価値です。

## 検証

リポジトリには`.opencode/tests/`の下に3つのチェックスクリプトが含まれています。レイヤー0は完全自動です; レイヤー1–2はOpenCode内で進むガイド付きチェックリストです。

```bash
# レイヤー0 — 静的チェック (自動, 0トークン)
pwsh .opencode/tests/T0-static-verify.ps1
# 期待される結果: すべてPASS / FAIL=0 (システムレベルのキーで、WARNもPASSとしてカウントされます)

# 3つのレイヤーを一度に実行
pwsh .opencode/tests/run-all.ps1
```

| スクリプト                    | レイヤー | 何をするか                                                                            | モード                 |
| ------------------------- | ----- | --------------------------------------------------------------------------------------- | -------------------- |
| `T0-static-verify.ps1`    | 0     | ファイル構造、エージェント/コマンド/スキルのカウント、READMEアンカー、キーのパスの正確性をチェック | 自動                 |
| `T1-behavioral-guide.ps1` | 1     | ルーティング / 意見 / 融合の動作のためのステップバイステップのチェックリストを表示                 | 手動 (OpenCode内) |
| `T2-moa-smoke-guide.ps1`  | 2     | `/moa-*`コマンドのエンドツーエンドのスモークテストチェックリストを表示                          | 手動 (OpenCode内) |
| `run-all.ps1`             | 0–2   | T0を実行し、その後T1/T2のガイド付きチェックリストを表示                                         | 混合                |

## FAQ

### インストール

**Q: すでに opencode.json がある場合、上書きされますか？**
A: いいえ。インストールスクリプトは MoA の `permission`、`agent`、`default_agent` 設定をマージし、既存の `provider`、`model` などを保持します。元のファイルは `.bak.timestamp` として自動バックアップされます。

**Q: Windows には `cp` コマンドがないのですが、どうすればいいですか？**
A: `Copy-Item` または `xcopy` を使用してください：

```powershell
# PowerShell
Copy-Item -Recurse -Force opencode-moa\.opencode .\.opencode
# CMD
xcopy opencode-moa\.opencode .\.opencode /E /I /Y
```

**Q: pwsh/jq なしでインストールできますか？**
A: はい。方法 1 (AI 自動デプロイ) または方法 3 (手動設定マージ) を使用してください。

**Q: デスクトップアプリでのインストール方法は？**
A: 方法 1 が最も便利です — `docs/opencode-moa.en.md` をチャットボックスにドラッグして AI に自動デプロイさせてください。方法 2/3 は最初にターミナル (CMD/PowerShell/Terminal) で操作する必要があります。

### 使用法

**Q: "concierge-router" が見えませんか？**
A: "30秒デプロイ → デプロイ成功の確認方法" の下の3つのチェックを確認してください：プロジェクトルートの `opencode.json`、`.opencode/agents/` 下の22の .md、再起動後に `Tab` で切り替え（Windows デスクトップクライアントでは `Ctrl+.` も機能します）。

**Q: `@tool-handler` から応答がありませんか？**
A: `.opencode/agents/tool-handler.md` が存在し、フロントマター形式が正しいことを確認してください。

**Q: "model not found" エラー？**
A: モデル ID 形式は `provider/model-id` である必要があります（例： `opencode-go/kimi-k2.7-code`）。対応するプロバイダーを設定ファイルに登録してください（システムレベルの `~/.config/opencode/opencode.json` またはプロジェクトの `opencode.json`）、その後 TUI 内で `/models` を使用して利用可能なモデルを確認してください。

**Q: 元のビルド/プランエージェントに戻すにはどうすればいいですか？**
A: `Tab` を押して切り替えます（Windows デスクトップクライアントでは `Ctrl+.` も機能します）、または `/build`、`/plan` と入力します。MoA は組み込みエージェントに影響を与えません。

**Q: Go プランではなく、自分のモデルを使用したいのですが？**
A: エージェントの `model` フィールドを変更するだけです：

```yaml
# .opencode/agents/mid-eng.md
model: opencode-go/glm-5.2
```

**Q: デプロイ後にリポジトリを削除できますか？**
A: はい。MoA はすでにプロジェクトの `.opencode/` ディレクトリにコピーされていますので、元のリポジトリは削除できます。

**Q: 複数のプロジェクトにデプロイするにはどうすればいいですか？**
A: 各プロジェクトを個別にデプロイしてください。`.opencode/` はプロジェクトレベルの設定であり、他のプロジェクトには影響しません。

### フォールバック

**Q: ツールレイヤー全体がダウンした場合、どうすればいいですか？**
A: 上記の "フォールトトレランス設計 → フォールバックチェーン" を参照してください：MoA はユーザーに A. 数分待つ / B. ツールレイヤーをスキップしてオピニオンレイヤーを直接呼び出す（コストが高くなる）ことを選択させます。

**Q: 無料モデルはどこにありますか？**
A: 上記の "コスト → 無料モデル" を参照してください：`/models` を使用してモデルリストを開き、「無料」とタグ付けされたものを選択してください（Windows デスクトップクライアントでは `Ctrl+'` も機能します）（DeepSeek V4 Flash Free、MiMo-V2.5 Free、North Mini Code Free など）。無料モデルはコンテキストが制限されており、遅くなる可能性があり、データはトレーニングに使用される場合があります。
