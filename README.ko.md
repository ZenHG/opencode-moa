OpenCode MoA는 OpenCode를 위한 에이전트 혼합 구성 패키지입니다. 여러 모델이 **동시에 같은 문제에 대해 생각**한 다음, 단일 모델이 도달할 수 없는 출력 품질로 융합됩니다. 도구를 전환하거나 코드를 작성하거나 API 할당량을 가질 필요가 없습니다 — 파일을 프로젝트에 드롭하고 OpenCode를 재시작하기만 하면 됩니다.

**22개의 에이전트 · 5개의 명령어 · 3개의 기술 · 30초 배포**

## 왜 이게 필요할까요?

기본적으로 OpenCode는 시작부터 끝까지 단일 모델을 사용합니다. 하나의 문자를 변경하고 시스템 아키텍처를 설계하는 데 동일한 프롬프트, 동일한 온도, 동일한 컨텍스트를 사용합니다. 노동 분업이 없습니다.

**세 가지 문제:**

1. **비용 통제 불능** — 간단한 작업도 비싼 모델을 사용하여 월 청구서가 높게 유지됩니다.
2. **품질 병목 현상** — 단일 모델은 사고 방식이 하나뿐이며, 쉽게 맹점에 갇힙니다.
3. **내결함성 없음** — 모델이 죽으면 멈추고, 대체 수단이 없습니다.

**MoA의 해결책:**

```

You: help me design a message queue solution

    ┌─ flag-arch (Qwen3.7 Max)  ─── 건축가의 관점에서 계획
    ├─ flag-plan (GLM 5.2    )  ─── PM의 관점에서 계획
    ├─ flag-eng  (MiniMax M3 )  ─── 구현자의 관점에서 계획
    └─ flag-fuse (Kimi K3    )  ─── 각자의 최선을 취하여 하나의 최적 솔루션
```

세 개의 독립적인 계획이 세 개의 서로 다른 모델에서 자연스럽게 "합의 + 분기" 구조를 형성합니다. 융합 모델은 무엇이 합의인지 식별하고 이를 유지하며, 분기된 부분에서 최선을 취합니다 — 단일 모델이 할 수 없는 작업입니다.

### 선택 사항 (설치 스크립트에서 필요)

| 요구 사항         | 확인 명령어    | 비고                                                                     |
| ----------------- | ---------------- | ------------------------------------------------------------------------- |
| PowerShell Core    | `pwsh --version` | install.ps1에서 필요, Windows에 번들로 포함되거나 `brew install powershell`로 설치  |
| jq                | `jq --version`   | JSON 병합을 위한 install.sh에서 필요, `apt install jq` / `brew install jq` |

> pwsh/jq가 없어도 괜찮습니다 — 방법 1(AI 자동 배포) 또는 방법 3(수동 병합)을 사용할 수 있습니다.

### 데스크탑 vs CLI

- **CLI**: 모든 방법 지원
- **데스크탑**: 방법 1(AI 자동 배포)이 가장 편리합니다; 방법 2/3은 먼저 터미널 작업이 필요합니다.

> ⚠️ **시스템 수준 키 경로를 잘못 배치하기 쉽습니다** — 아래 "배포 전에 읽기"에서 올바른 철자를 확인하세요. 잘못된 경로는 배포가 성공한 것처럼 보이지만 모든 에이전트가 연결되지 못하게 됩니다.

> ⚠️ **배포 전에 읽기: 키 경로를 잘못 배치하지 마세요**
> 제공자 + 키를 **프로젝트 수준 `opencode.json`** (기본값, 독립형) 또는 **시스템 수준** 공유 경로 중 하나에 넣으세요 — **하나**를 선택하세요.
> 시스템 수준을 사용하는 경우, 올바른 경로는:
> 
> - Linux/macOS `~/.config/opencode/opencode.json`
> - Windows `%USERPROFILE%\.config\opencode\opencode.json` (**아니요** `%APPDATA%\opencode`)
>   잘못된 시스템 수준 경로는 "배포가 성공하지만 모든 에이전트가 연결할 수 없음"으로 이어집니다.

## 30초 배포

### 방법 1: AI 자동 배포 (권장)

1. [`docs/opencode-moa.en.md`](https://github.com/ZenHG/opencode-moa/blob/master/docs/opencode-moa.en.md) 다운로드
2. OpenCode에 해당 문서를 업로드하고 전송:

> 현재 프로젝트에 이 매뉴얼에서 22개의 에이전트, 5개의 명령어 및 3개의 기술을 배포합니다.

3. AI가 모든 파일을 자동으로 생성합니다. **완료되면 OpenCode를 재시작하세요.**

> 파일을 수동으로 생성할 필요가 없습니다. 배포 매뉴얼 자체가 설치 프로그램입니다.

### 방법 2: 원클릭 설치 스크립트 (스크립트 버전 · CLI 친화적)

```bash
# 레포 클론
git clone https://github.com/ZenHG/opencode-moa.git

# 프로젝트 디렉토리로 이동
cd your-project

# 레포에서 .opencode 디렉토리와 .moa 구성 복사
cp -r ../opencode-moa/.opencode/ .
cp -r ../opencode-moa/.moa/ .

# 설치 스크립트 실행 (구성 자동 병합, API 키 유지)
# Windows:
pwsh ../opencode-moa/install.ps1
# Linux/macOS:
bash ../opencode-moa/install.sh
```

> 설치 스크립트는 원본 `opencode.json`을 자동으로 백업하며, 제공자와 API 키를 유지하면서 MoA 구성을 병합합니다.
> 
> 참고: 이 방법은 레포의 번들된 `.opencode/`를 그대로 복사합니다 — 그 에이전트는 **중국어 표시 이름**을 가집니다. 영어 이름의 에이전트를 원하시면(그래서 `@english-name`을 사용할 수 있도록) 방법 1을 대신 사용하세요.

### 모델 사용자 정의

MoA는 **일반 템플릿**입니다 — 각 에이전트의 모델은 변경할 수 있는 ID입니다. 각 에이전트 파일은 다음으로 시작합니다:

```yaml
model: opencode-go/<model-id>
```

모델을 교체하려면, `.opencode/agents/<agent>.md`에서 해당 한 줄을 접근할 수 있는 `provider/model-id`로 편집하세요 (예: `opencode-go/kimi-k2.7-code`, `opencode-go/glm-5.2`). 재설치가 필요 없습니다. 자유롭게 혼합하고 매치하세요 — 템플릿은 여러분을 구속하지 않습니다.

### 방법 3: 수동 설치

```bash
# 1. 레포 클론
git clone https://github.com/ZenHG/opencode-moa.git

# 2. .opencode 디렉토리와 .moa 구성 복사
cp -r opencode-moa/.opencode/ your-project/
cp -r opencode-moa/.moa/ your-project/

# 3. opencode.json 수동 병합 (직접 교체하지 마세요!)
# opencode.json을 열고 MoA의 permission.task 및 agent 섹션을 병합하세요.
# 기존 제공자 및 모델 구성을 유지하세요.
```

> ⚠️ **절대** `cat >>`를 사용하여 추가하지 마세요 — JSON 형식이 손상됩니다. **직접 교체하지 마세요** — API 키를 잃게 됩니다.
> 
> 참고: 이 방법은 레포의 번들된 `.opencode/`를 그대로 복사합니다 — 그 에이전트는 **중국어 표시 이름**을 가집니다. 영어 이름의 에이전트를 원하시면(그래서 `@english-name`을 사용할 수 있도록) 방법 1을 대신 사용하세요.

### 배포 성공 여부 확인 방법

1. OpenCode를 재시작한 후, `Tab`을 눌러 에이전트를 순환하고 "concierge-router"를 확인하세요.
2. `@tool-handler`를 입력하면 응답합니다.
3. 검증 스크립트를 실행하세요: `pwsh .opencode/tests/T0-static-verify.ps1` (배포 중 수동 블록 5.5에 의해 생성됨), 예상 결과는 모두 PASS(FAIL=0; 시스템 수준 키가 있는 경우, WARN도 PASS로 간주됨)입니다.

### 원클릭 롤백

```bash
rm -rf your-project/.opencode/
rm -rf your-project/.moa/
# 수동으로 opencode.json을 복원하세요 (설치 스크립트가 자동으로 .bak 파일을 백업합니다.)
```

## 사용 방법은?

**아무것도 배우지 마세요 — 그냥 이야기하세요.** 컨시어지-라우터는 자동으로 작업 복잡성을 판단하고 해당 에이전트 체인을 배치합니다.

| 당신이 말하는 것                       | 컨시어지-라우터가 하는 일                                        | 사용된 에이전트                     |
| -------------------------------------- | -------------------------------------------------------------- | ----------------------------------- |
| "이 변수를 이름 변경해줘"              | 간단한 작업으로 판단                                          | swift (Flash)                       |
| "사용자 인증 모듈을 작성해줘"           | 도구 계층 수집 → 3 중간 계층 병렬 → 융합                       | tool-handler + mid-tier trio + fuse |
| "마이크로서비스 아키텍처를 설계해줘"   | 도구 계층 수집 → 3 플래그십 병렬 → 융합 → 구현 → QA          | full-chain 6 agents                 |
| "이 스크린샷의 UI를 복원해줘"          | 3 프론트엔드 전문가 병렬 → 리드가 최선 선택                    | frontend quartet                    |
| 스크린샷이 포함된 메시지                | 비전-번역기가 텍스트로 변환 → 일반 라우팅                     | vision-translator                   |
| 오류 로그 / 다이어그램 / 복잡한 콘텐츠가 포함된 메시지 | 비전-번역기가 콘텐츠를 분해 → 일반 라우팅                     | vision-translator (백업 역할)       |

**직접 `@` 호출:**

```
@swift help me write a hello world
@tool-handler search all TODOs in the project
@flag-arch design a message queue solution
```

| --------------- | ---------------------------------------------- |
| `/moa-quick`    | 간단한 작업, 번역, 구성 변경                   |
| `/moa-medium`   | 기능 모듈, 버그 수정, 단일 파일 리팩토링      |
| `/moa-flagship` | 시스템 아키텍처, 대규모 리팩토링               |

### 자동 라우팅 (v0.0.15)

컨시어지-라우터는 이제 키워드 분석을 기반으로 작업 유형을 자동 감지합니다:

- **탐색 작업**: "분석하다", "비교하다", "이해하다", "조사하다" → 탐색 프롬프트 + 동결된 수용 기준
- **실행 작업**: "수정하다", "추가하다", "구현하다", "배포하다" → 실행 프롬프트 + 손실 방지 규칙
- **작업 유형은 파이프라인 출력에 나타납니다**: `[Type: Execute]` 또는 `[Type: Explore]`

## 아키텍처

```
                      concierge-router (Flash)
                                 │
                ┌────────────────┼─────────────────┐
                ▼                ▼                 ▼
             Tool layer     Opinion layer       Fusion layer
             Flash + MiMo   3 parallel opinions take the best
             (~80% calls)   (~18% calls)        (~2% calls)
```

**도구 계층** (Flash + MiMo) — 코드 읽기, 파일 검색, 스크린샷을 텍스트로 변환. 저렴하고 빠르며 자유롭게 호출하세요.

**의견 계층** (MiniMax / DeepSeek Pro / Qwen / MiMo-Pro) — 다양한 관점에서의 계획. 세 가지 의견이 자연스럽게 "합의 + 분기" 구조를 형성합니다.

**융합 계층** (Kimi K3 / Qwen-Max / GLM / DeepSeek Pro 백업) — 합의를 유지하고 분기에서 최선을 선택하며, 융합 실패 시 DeepSeek V4 Pro로 백업합니다. 플래그십 융합은 현재 **Kimi K3** (2.8T 파라미터, 1M 컨텍스트, 최상급 프론티어 모델)에서 실행되고 있으며, MoA의 품질 한계를 선두로 끌어올리고 있습니다.

> ⚠️ 아래의 호출-볼륨 비율 (~80% / ~18% / ~2%)는 **설계 목표**이며, 측정된 통계가 아닙니다. 실제 비율은 작업 복잡성에 따라 다릅니다.

### 구조화된 출력

의견 및 융합 에이전트는 `---section-name---` 마커를 사용합니다. 의견 계층: `---memory---` + `---plan---` + `---NOT---`. 융합 계층: 메타데이터, 합의, 계획, NOT 목록 및 수용 기준이 포함된 전체 구조. 하류 파싱 및 동결된 수용 검증을 가능하게 합니다.

### 반부정행위 방지 (v0.0.15)

구현 에이전트가 절차를 간소화하지 못하도록 방지합니다: 기본 비회귀, 금지된 행동 (테스트 건너뛰기/모의/삭제), 숨겨진 점검, 구현 차이 검사, 손실 방지 (항목당 3회 재시도, 비회귀 시 롤백). 수용 기준 템플릿은 `.moa/acceptance-template.json`에 있습니다.

## 22 에이전트

> 영어 이름은 논리적 역할을 나타내며; 괄호 안의 중국어는 `.opencode/agents/` 아래의 **정확한 파일 이름**입니다 — `@`로 호출합니다 (예: `@门童路由员`).

```
concierge-router (门童路由员, Flash)
 │
 ├── 도구 계층 ─────────────────────────────────────────────
 │   tool-handler      (工具人, Flash    ) 코드 읽기, 파일 검색
 │   tool-handler-mimo (工具人-mimo, MiMo) [숨김] 신뢰할 수 있는 파일 읽기 (백업 + 병렬)

## 내결함성 설계

### 도구 계층 폴백 체인

도구 계층이 실패하더라도 멈추지 않고 자동으로 다운그레이드됩니다:

```
tool-handler (Flash) 실패 → 즉시 한 번 재시도
  → 재시도 성공 → 정상적으로 반환
  → 재시도 실패 → tool-handler-mimo (MiMo) 실패 → 즉시 한 번 재시도
    → 재시도 성공 → 정상적으로 반환
    → 재시도 실패 → 사용자에게 요청:
      A. 몇 분 기다렸다가 재시도
      B. 도구 계층을 건너뛰고 의견 계층을 직접 호출 (비용 증가)
      C. 무료 모델로 전환
```

> 대부분의 공급자 오류 (502/503/타임아웃)는 일시적입니다; 빠른 재시도가 보통 성공합니다.

### 융합 계층 폴백

주요 융합 에이전트가 실패할 경우 (STUCK / ERROR_PROVIDER / 타임아웃 / 빈 결과), 컨시어지-라우터는 자동으로 `@融合·保底` (DeepSeek V4 Pro, 폴백)으로 전환됩니다:

```
flag-fuse (旗舰·融合, Kimi K3) 실패
  → 작업(@融合·保底) (DeepSeek V4 Pro) → 폴백 결과 출력
mid-fuse (中级·融合, Kimi) 실패
  → 작업(@融合·保底) (DeepSeek V4 Pro) → 폴백 결과 출력
fe-lead (前端·总工, GLM-5.2) 실패
  → 작업(@融合·保底) (DeepSeek V4 Pro) → 폴백 결과 출력
```

폴백 에이전트는 동일한 잔여 강화 융합 프로세스를 사용합니다.

### 의견 계층 부분 실패 내결함성

개별 의견 에이전트 (아키텍처/계획/엔지니어링, 프론트엔드 복원/논리/모션, 중간 계층 엔지니어링/창의성/코딩)는 독립적으로 빈 결과를 반환하거나 타임아웃될 수 있습니다. 시스템은 이를 우아하게 처리합니다:

```
3개의 병렬 의견 에이전트 배치
  → 어떤 에이전트가 빈 결과를 반환 → 해당 에이전트를 한 번 재시도
    → 재시도 성공 → 정상적으로 계속
    → 재시도 실패 → "저하"로 표시하고 N/3 입력으로 진행
      → 残差提取者는 사용 가능한 입력만 작업
      → 旗舰·融合은 저하된 융합 규칙을 적용
      → 출력에 "[부분] N/3 입력" 레이블 부착
      → 신뢰 점수는 하향 조정
```

저하된 융합 규칙 (N < 3):
- 합의 범위 분모는 N이며, 3이 아닙니다.
- 누락된 관점은 `[Missing: 관점 이름]`으로 레이블이 붙습니다.
- 합의 범위 < 50%는 "낮은 신뢰 저하된 융합" 경고를 발생시킵니다.
- 단일 출처 융합 (N=1)은 0.7 신뢰 패널티 계수를 적용합니다.

> 이는 하나의 의견 에이전트가 실패할 때 파이프라인이 멈추는 것을 방지합니다 (STUCK) — 일반적인 사용자 불만입니다.

### 선언적 에이전트 전제조건

에이전트 활성화는 선언적 `precondition` 메타데이터에 의해 결정되며, 하드코딩된 라우팅 규칙이 아닙니다. 각 에이전트는 활성화되어야 할 때를 선언합니다:

| 에이전트 | 전제조건 |
|-------|---------------|
| 闪电侠 | 항상 |
| 工具人 | 코드베이스 컨텍스트 필요 |
| 视觉翻译官 | 주요: `screenshot`; 폴백: `error_log OR diagram OR long_document OR ambiguous_intent` |
| 中级·工程 | 엔지니어링 복잡성 필요 |
| 中级·创意 | 창의성 복잡성 필요 |
| 中级·码农 | 구현 복잡성 필요 |
| 旗舰·架构/规划/工程 | 시스템 설계 복잡성 필요 |
| 前端·还原/逻辑/动效 | 프론트엔드 작업 필요 |
| 融合·保底 | 융합 계층이 실패하거나 의견 계층이 부분 결과를 반환할 때 활성화 |

조건 활성화는 단락 회로 논리를 따릅니다: 전제조건 충족 → 활성화; 충족되지 않음 → 사용자에게 확인 요청. 이는 하드코딩된 트리거 규칙 ("스크린샷 사용 가능 → @vision-translator")을 에이전트 선언, 자기 문서화된 전제조건으로 대체합니다.

### 파이프라인 단계 시각화

모든 라우팅 결정은 단계 식별자를 출력하여 사용자가 내부 단계 번호를 배우지 않고도 파이프라인 진행 상황을 추적할 수 있도록 합니다:

```
[Stage: Tool Layer] → [Stage: Opinion Layer] → [Stage: Fusion Layer] → [Stage: Implementation Layer]
```

단계-단계 매핑:
- `Tool Layer` — 자재 수집 단계
- `Opinion Layer` — 병렬 계획 설계 단계 (중간 계층 / 플래그십 / 프론트엔드)
- `Fusion Layer` — 계획 융합 및 검증 단계
- `Implementation Layer` — 코드 구현 및 수용 단계

### 통합 진행 보고

성공 경로와 실패 경로 모두 동일한 보고 형식을 따르며, 내부 에이전트 이름을 노출하지 않습니다:

```
[Pipeline] mode=<lite|balanced|strict>  stage=<Tool Layer|Opinion Layer|Fusion Layer|Implementation Layer>  status=<idle|in_progress|complete|degraded|stuck>
  reason: <이 단계의 이유>
  path: <Tool Layer|Mid-tier chain|Flagship chain|Frontend chain>
  fallback: <복구 전략>
```

상태 지표:
- `in_progress` — 현재 단계 실행 중
- `complete` — 단계가 성공적으로 완료됨
- `degraded` — 부분 입력으로 실행 중, 신뢰도 낮음
- `stuck` — 모든 복구 경로 소진, 사용자 개입 필요

### 신속 병렬 단축키

주 파이프라인이 실행 중일 때, 신속은 독립적인 간단한 하위 작업을 위해 병렬로 배치될 수 있습니다:

```
Main pipeline: Tool Layer → Opinion Layer → Fusion Layer → Implementation Layer
Parallel lane: swift (항상 준비, 주 파이프라인과 함께 실행)
```

트리거 조건 (하나라도):
- 사용자 지침이 명시적으로 병렬 작업을 요청 ("X를 동시에 수행", "Y도 빠르게 확인")
- 주 파이프라인 실행 중 간단한 하위 작업이 발생 (예: 아키텍처 계획이 설계되는 동안 TODO 검색)
- 사용자가 직접 @swift 호출

범위 제한:
- ✅ 주 파이프라인 출력에 의존하지 않는 독립적인 작업
- ✅ 간단한 작업: 파일 검색, grep, 구성 쿼리, 포맷팅
- ❌ 주 파이프라인에 입력을 생성하는 작업
- ❌ 의견 융합 작업 (직렬로 유지해야 함)
- ❌ 구현 및 QA 작업 (직렬로 유지해야 함)

신속이 주 파이프라인보다 먼저 완료되면 결과는 보류되고 마지막에 함께 반환됩니다. 주 파이프라인이 먼저 완료되면 신속 결과가 즉시 반환됩니다. 신속 실패는 주 파이프라인 실행에 영향을 미치지 않습니다.

### MCP 권한 격리

의견 계층 에이전트는 코드를 직접 읽는 것이 금지되어 있습니다 (`read: deny` + `bash: deny`), 이를 통해 도구 계층을 우회하여 자재를 직접 가져오는 것을 방지합니다:

- 도구 계층: 코드를 읽고 파일을 검색할 수 있습니다 ( `read`/`bash` 접근 가능)
- 의견 계층: `read: deny` + `bash: deny`, 도구 계층의 자재를 기반으로 계획만 가능
- 융합 계층: 동일한 제한, 세 가지 의견을 기반으로 융합만 가능

> 참고: 이 프로젝트는 MCP 서버를 구성하지 않습니다. "MCP 권한 격리"라는 용어는 에이전트 수준의 도구 제한 (`read: deny` / `bash: deny`)을 의미하며, MCP 서버 수준의 격리가 아닙니다.

### 작업 중첩 방어

모든 비라우팅 에이전트는 `task: deny`를 선언하여 자식 에이전트가 다시 task()를 호출하는 것을 방지하고 재귀 중첩을 차단합니다:

- **1단계 (에이전트 전면)**: 각 에이전트 파일은 `task: deny`를 선언합니다.
- **2단계 (opencode.json)**: `permission.task`는 컨시어지가 에이전트를 호출하는 것만 허용하며, 비라우팅 에이전트는 작업자를 호출하는 것이 전역적으로 금지됩니다.
- **3단계 (프롬프트 가드)**: 컨시어지 프롬프트는 하위 에이전트를 통해 새로운 파이프라인을 시작하지 못하도록 제약으로 끝납니다.

> 2026-07에 추가됨, 컨시어지→tool-handler→tool-handler 삼중 중첩 발견 후. 세 단계의 중복성은 한 단계가 실패하더라도 차단을 보장합니다.

### 자재 없음 폴백

의견 계층이 호출되지만 자재가 없을 경우 (도구 계층이 완전히 실패), 사용자에게 요청합니다:

- "계획을 직접 제공" 선택 → 요구 사항 설명에 기반한 순수 논리적 추론 (코드 읽기 없음)
- "도구 계층을 기다리기" 선택 → WAITING 출력, 도구 계층이 복구된 후 재시도

### 오류 분류

도구 계층은 실패 시 명확한 오류 범주를 출력하며, 맹목적으로 재시도하지 않습니다:

- `ERROR_PROVIDER` — 서버 502/503/타임아웃
- `ERROR_AUTH` — 인증 실패
- `ERROR_UNKNOWN` — 기타 오류

## 검증

리포지토리는 `.opencode/tests/` 아래에 세 개의 체크 스크립트를 제공합니다. 레이어 0은 완전 자동화되어 있으며, 레이어 1-2는 OpenCode 내에서 진행하는 가이드 체크리스트입니다.

```bash
# 레이어 0 — 정적 체크 (자동, 0 토큰)
pwsh .opencode/tests/T0-static-verify.ps1
# 예상: 모두 PASS / FAIL=0 (시스템 수준 키로, WARN도 PASS로 계산됨)

# 세 개의 레이어를 동시에 실행
pwsh .opencode/tests/run-all.ps1
```

| 스크립트                    | 레이어 | 수행하는 작업                                                                          | 모드                 |
| --------------------------- | ----- | ------------------------------------------------------------------------------------- | -------------------- |
| `T0-static-verify.ps1`      | 0     | 파일 구조, 에이전트/명령/기술 수, README 앵커, 키 경로 정확성 체크                 | 자동                 |
| `T1-behavioral-guide.ps1`   | 1     | 라우팅 / 의견 / 융합 동작에 대한 단계별 체크리스트 출력                           | 수동 (OpenCode 내)   |
| `T2-moa-smoke-guide.ps1`    | 2     | `/moa-*` 명령에 대한 스모크 테스트 체크리스트 출력                                | 수동 (OpenCode 내)   |
| `run-all.ps1`               | 0–2   | T0를 실행한 후 T1/T2 가이드 체크리스트 출력                                       | 혼합                 |

## FAQ

### 설치

**Q: 나는 이미 opencode.json이 있는데, 덮어씌워질까요?**
A: 아니요. 설치 스크립트는 MoA의 `permission`, `agent`, `default_agent` 구성을 병합하며, 기존의 `provider`, `model` 등을 유지합니다. 원본 파일은 `.bak.timestamp`로 자동 백업됩니다.

**Q: Windows에는 `cp` 명령어가 없는데, 어떻게 하나요?**
A: `Copy-Item` 또는 `xcopy`를 사용하세요:

```powershell
# PowerShell
Copy-Item -Recurse -Force opencode-moa\.opencode .\.opencode
# CMD
xcopy opencode-moa\.opencode .\.opencode /E /I /Y
```

**Q: pwsh/jq 없이 설치할 수 있나요?**
A: 네. 방법 1 (AI 자동 배포) 또는 방법 3 (수동 구성 병합)을 사용하세요.

**Q: 데스크탑 앱에서 어떻게 설치하나요?**
A: 방법 1이 가장 편리합니다 — `docs/opencode-moa.en.md`를 채팅 상자로 드래그하여 AI가 자동 배포하도록 하세요. 방법 2/3은 먼저 터미널(CMD/PowerShell/Terminal)에서 작업해야 합니다.

### 사용법

**Q: "concierge-router"가 보이지 않나요?**
A: "30초 배포 → 배포 성공 여부 확인 방법" 아래의 세 가지 체크를 확인하세요: 프로젝트 루트의 `opencode.json`, `.opencode/agents/` 아래의 22 .md, 재시작 후 `Tab`으로 전환 (Windows 데스크탑 클라이언트: `Ctrl+.`도 작동합니다).

**Q: `@tool-handler`가 응답하지 않나요?**
A: `.opencode/agents/tool-handler.md`가 존재하는지 확인하고 프론트매터 형식이 올바른지 확인하세요.

**Q: "모델을 찾을 수 없습니다" 오류는 무엇인가요?**
A: 모델 ID 형식은 `provider/model-id`여야 합니다 (예: `opencode-go/kimi-k2.7-code`). 해당 제공자를 구성 파일에 등록한 후 (시스템 수준 `~/.config/opencode/opencode.json` 또는 프로젝트 `opencode.json`), TUI 내에서 `/models`를 사용하여 사용 가능한 모델을 확인하세요.

**Q: 원래의 빌드/계획 에이전트로 어떻게 돌아가나요?**
A: `Tab`을 눌러 전환하세요 (Windows 데스크탑 클라이언트: `Ctrl+.`도 작동합니다), 또는 `/build`, `/plan`을 입력하세요. MoA는 내장 에이전트에 영향을 미치지 않습니다.

**Q: Go 계획이 아닌 내 모델을 사용하고 싶어요?**
A: 에이전트의 `model` 필드를 변경하세요:

```yaml
# .opencode/agents/mid-eng.md
model: opencode-go/glm-5.2
```

**Q: 배포 후 레포를 삭제할 수 있나요?**
A: 네. MoA는 이미 프로젝트의 `.opencode/` 디렉토리에 복사되어 있으므로 원본 레포를 삭제할 수 있습니다.

**Q: 여러 프로젝트에 걸쳐 배포하려면 어떻게 하나요?**
A: 각 프로젝트를 별도로 배포하세요. `.opencode/`는 프로젝트 수준의 구성이며 다른 프로젝트에 영향을 미치지 않습니다.

### 폴백

**Q: 전체 도구 레이어가 다운되었어요, 이제 어떻게 하나요?**
A: 위의 "내결함성 설계 → 폴백 체인"을 참조하세요: MoA는 사용자에게 A. 몇 분 기다리기 / B. 도구 레이어를 건너뛰고 의견 레이어를 직접 호출하도록 요청합니다 (비용이 더 높습니다).

**Q: 무료 모델은 어디에 있나요?**
A: 위의 "비용 → 무료 모델"을 참조하세요: `/models`를 사용하여 모델 목록을 열고 "무료"로 태그된 모델을 선택하세요 (Windows 데스크탑 클라이언트: `Ctrl+'`도 작동합니다) (DeepSeek V4 Flash Free, MiMo-V2.5 Free, North Mini Code Free 등). 무료 모델은 제한된 컨텍스트를 가지며, 속도가 느릴 수 있고 데이터가 훈련에 사용될 수 있습니다.

## 유지보수 도구 (최종 사용자에게 필요하지 않음)

다음 파일은 **레포 유지보수자**를 위한 것이며, MoA 배포를 위한 것이 아닙니다. 최종 사용자는 무시해도 됩니다.

| 파일                          | 목적                                                                                                                                               |
| ----------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| `deploy-sync.ps1`            | 유지보수자 전용 — 레포를 GitHub에 동기화하고 `opencode-moa` 기술을 SkillHub에 업로드합니다. `-SkipGit` / `-SkipSkillHub` / `-DryRun`을 지원합니다.   |
| `scripts/hooks/pre-commit`    | 로컬 git 훅 알림: `CHANGELOG.md` 변경 사항을 스테이징할 때 경고합니다 (푸시 시 자동 릴리스됨).                                                        |
| `scripts/hooks/pre-push`      | 로컬 git 훅 알림: `CHANGELOG.md` 변경 사항을 `master`에 푸시하기 전에 버전을 확인합니다; 비대화형/CI 환경에서는 자동으로 진행됩니다.                  |

> 이러한 훅은 자동으로 설치되지 않습니다. 알림을 원하시면 `.git/hooks/`에 심볼릭 링크를 생성하세요, 예: `ln -s ../../scripts/hooks/pre-push .git/hooks/pre-push`.
